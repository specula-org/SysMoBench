## Modeling Requirements

### MANDATORY CORE ACTIONS (must include all):

1. **Message Types**:
   - MsgHup (election timeout)
   - MsgVote/MsgVoteResp (voting)
   - MsgApp/MsgAppResp (log replication)

2. **Node States** - Four states:
   - StateFollower
   - StateCandidate
   - StateLeader
   - StatePreCandidate (prevote enabled)

3. **Leader Election** - Complete prevote + vote phases:
   - PreCandidate -> Candidate -> Leader transitions

4. **Log Operations**:
   - Log entry appending
   - Consistency checks
   - Commitment with majority quorum

5. **Heartbeat/Timeout**:
   - Election timeouts triggering campaigns
   - Heartbeat prevention of elections

6. **Client Proposals**:
   - MsgProp message handling
   - Log entry creation by leaders

### EXPLICITLY EXCLUDED (do not model):

- Configuration changes and joint consensus (ConfChange messages)
- Log compaction and snapshots (MsgSnap)
- ReadIndex optimizations (MsgReadIndex)
- Async storage operations (LocalAppendThread, LocalApplyThread)
- Advanced flow control and progress tracking details

### REQUIRED BEHAVIORAL SCOPE:

- **Prevote phase**: StatePreCandidate must be modeled as it's enabled by default in etcd
- **State transition constraints**: Follower -> PreCandidate -> Candidate -> Leader (strict transitions)
- **Message processing by state**: only valid message types handled in each node state
- **Term advancement rules**: nodes advance term when receiving messages with higher term
- **Voting restrictions**: one vote per term, term must be current or newer
- **Heartbeat mechanism**: leaders send heartbeats, followers reset election timeout on receipt
- **Log consistency checks**: prevLogIndex/prevLogTerm validation in MsgApp processing
- **Majority-based**: leader election and log commitment require majority quorum
- **Network model**: basic message delays and losses

### SPECIFICATION REQUIREMENTS:

1. **MUST include EXTENDS statement**: The specification must extend at least these modules: TLC, Sequences, Naturals, FiniteSets
2. **TypeOK**: Define a TypeOK operator for type checking
3. **Spec Definition with Fairness**: The Spec definition MUST include appropriate fairness assumptions (WF_vars/SF_vars) to ensure liveness properties
4. **Next Operator Structure**: The 'Next' operator SHOULD be a disjunction of atomic actions
5. **DO NOT define invariants** (like LeaderUniqueness, LogMatching, etc.) - only include TypeOK, Init, actions, Next, Spec, and Vars

## Output Requirements

You must generate TWO files in the `./output/` directory:

1. **TLA+ Specification**: `./output/{spec_module}.tla`

2. **TLC Configuration**: `./output/{spec_module}.cfg`

- If `success` is false, read the `output_file` to understand the errors
