## Modeling Requirements

### MANDATORY CORE ACTIONS (must include all):

1. **Message Types** - request, produce

2. **Node States** - Four states: c, c1, c2, p, p1, p2

### EXPLICITLY EXCLUDED (do not model):

- MPCalContext management
- Goroutine setup and teardown
- Advanced flow control and progress tracking details

### REQUIRED BEHAVIORAL SCOPE:

- Produce-consume Cycle: c → c1 → p → p1 → p2 → c2
- One single Producer and any number of consumers
- Simple FIFO network

### EVALUATION METHOD:

Your specification will be validated against execution traces collected from the real system. For each observed state transition in a trace, we check whether one of your actions, applied from the trace's pre-state, reaches the trace's post-state in exactly one step. Each target action is graded independently (pass rate across sampled windows).

### SPECIFICATION REQUIREMENTS:

1. **MUST include EXTENDS statement**: The specification must extend at least these modules: TLC, Sequences, SequencesExt, Naturals, FiniteSets, Bags
2. **TypeOK**: Define a TypeOK operator for type checking
3. **Spec Definition with Fairness**: The Spec definition MUST include appropriate fairness assumptions (WF_vars/SF_vars) to ensure liveness properties
4. **Next Operator Structure**: The 'Next' operator SHOULD be a disjunction of atomic actions
5. **DO NOT define invariants** - focus on modeling the system behavior

## Output Requirements

You must generate TWO files in the `./output/` directory:

1. **TLA+ Specification**: `./output/{spec_module}.tla`
   - The MODULE name must be exactly "{spec_module}"
   - Pure TLA+ code only - no markdown code blocks
   - Start with: ---- MODULE {spec_module} ----
   - End with: ====

2. **TLC Configuration**: `./output/{spec_module}.cfg`
   - Define SPECIFICATION (e.g., Spec)
   - Define CONSTANTS appropriately
   - Do NOT include INVARIANT definitions (they will be added separately)

## Validation Tool

You have access to the `submit_spec` tool to validate your specification.

**Usage**: Call `submit_spec` with both `spec_content` and `config_content` parameters.

**Response format**:
```json
{{
    "success": true/false,
    "attempt": 1,
    "remaining_attempts": 2,
    "phase1_syntax": {{"success": true/false, "output_file": "path/to/phase1.log"}},
    "phase2_runtime": {{"success": true/false, "output_file": "path/to/phase2.log"}}
}}
```

- If `success` is false, read the `output_file` to understand the errors
- You have **{max_attempts} attempts** total - use them wisely
- Fix errors based on feedback and resubmit

## Workflow

1. Read and understand the source code in `./source_code/` thoroughly

3. Write both the specification (.tla) and configuration (.cfg) files
4. Call `submit_spec` with both contents to validate
5. If errors occur, read the output files to understand the issues
6. Fix the issues and resubmit
7. Once successful, ensure the final files are saved in `./output/`
